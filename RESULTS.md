**Provenance tags.** **MEASURED** = we ran it (where [docs/BENCHMARKS.md](docs/BENCHMARKS.md) says *regenerates*, the raw data is in `results/` and `tools/check_results.py` rebuilds the number; *published record* means the record is published as measured, without its raw data). **DERIVED** = computed from measurements (labelled). **SOURCED** = someone else's published number (labelled, never mixed into a MEASURED comparison).

**Hardware.** RTX 5090 desktop (x86); Jetson AGX Thor (JetPack 7.2.1, MAXN power mode); Jetson AGX Orin 64 GB (JetPack 6, MAXN power mode). Whether clocks were pinned (`jetson_clocks`, `nvidia-smi -lgc`) differs per run; it is stated in §1-3 and their records, and was not recorded for §4, §6 and §7. **TensorRT versions:** §1-2 use TensorRT 11.2 (5090), 10.13 (Thor, NGC container) and 10.3 (Orin, JetPack); §3 and §4 use 10.16 on the 5090 and Thor and 10.3 on Orin; §6 uses 10.16 on Thor and 10.3 on Orin (the 5090's version is not recorded there); §7 uses 11.2. Software versions are in each record and in `setup/`.

**Different inputs.** §1-3 time the *base* GR00T N1.5 model on one recorded frame from NVIDIA's simulated GR1 PickNPlace demo (26 joints: arms + hands); §4 and §7 time single engines on synthetic zero/random inputs of the same shapes. The closed loop (§5) runs the RoboCasa *post-trained* model on the milk task (29 joints: arms + hands + waist). GR00T pads both to 32 action dimensions internally.

## 1. Speed: the whole policy call, three compilation levels (MEASURED, 2026-10-12)

One `policy.get_action()` on one recorded frame of NVIDIA's simulated GR1 PickNPlace demo (camera image + joint state + instruction) → a 16-step action chunk, 4 denoise steps, fp16 TensorRT engines. One process per board alternates eager / hybrid / full-TensorRT blocks (eager, hybrid, full, hybrid, full, eager; 20 timed calls after 5 warm-up per block) so session drift cancels; two independent engine builds per board. *Hybrid* = only ViT, LLM and DiT as TensorRT engines, the rest PyTorch eager. *Full TensorRT* = NVIDIA's own N1.5 deployment path (`deployment_scripts/trt_model_forward`), all 7 modules as engines.

## 2. Denoise steps: cost vs solver deviation (RTX 5090, MEASURED)

Steps swept 1→32 (+ a 64-step near-converged reference), 5 episodes × 3 noise seeds, matched noise.

- **Full TensorRT (2026-10-12):** latency = **7.38 + 1.52 ms × steps** (r² = 0.99998); DYNAMIC (boost ~2857 MHz): clocks not locked.
- **PyTorch eager (2026-09-23):** latency = 18.7 + 3.49 ms × steps (r² = 0.99959); locked SM 2700 / MEM 14001 MHz (nvidia-smi -lgc/-lmc); measured under load 2692 MHz, 13801 MHz.

| Steps | Full TensorRT latency | Deviation vs 64-step ref, full TensorRT | Deviation, eager |
|---|---|---|---|
| 1 | 8.81 ms | 15.93 ± 17.07% | 15.91 ± 17.01% |
| 2 | 10.36 ms | 10.86 ± 13.22% | 10.83 ± 12.71% |
| 4 | 13.47 ms | 3.71 ± 0.97% | 3.79 ± 0.98% |
| 8 | 19.65 ms | 2.07 ± 0.60% | 2.11 ± 0.60% |
| 16 | 31.80 ms | 1.13 ± 0.22% | 1.18 ± 0.23% |
| 32 | 56.09 ms | 0.42 ± 0.05% | 0.51 ± 0.05% |

Deviation = rel-MAE of the 26-DoF × 16-step action chunk vs a 64-step reference on the same path (solver truncation, ~C/N: C = 17.257 compiled, 17.93 eager). It is **not** task success. Build-to-build: per-step [1.536, 1.511] ms, max step-count spread 1.719%.

**Where the time goes at 4 steps (full TensorRT, instrumented):** fixed 7.653 ms (transforms 2.0, ViT 1.932, LLM 1.982, VL self-attn 0.667, other 0.604 ms) + 1.5768 ms per step (DiT 1.3408, Euler-loop glue 0.0971, encoder 0.0714, decoder 0.0548 ms). Host + glue grows with steps on this path: 2.969 + 0.1088 ms/step.

Reproduce: `bash speed/run_denoise_sweep.sh`. Records: `results/speed/n15_5090_{denoise,stagetime}_{fulltrt,eager}_*.json`.

## 4. Two arms vs four arms (MEASURED, 2026-10-11)

Only the action encoder and decoder depend on the action dimension; the 4-arm head is a synthetic widening (action_dim 32 → 64, `speed/arms_2v4/widen_action_head_onnx.py`) — timing only, no accuracy claim.

Times are per *module call* (one encoder + one decoder invocation); a *policy call* runs them once per denoise step, so ×4.

| Board | Encoder + decoder, 2 arms | 4 arms | Δ per module call | Δ per policy call (×4 steps) |
|---|---|---|---|---|
| RTX 5090 | 0.041 ms | 0.04249 ms | +0.0015 ms | +0.006 ms |
| Jetson AGX Thor | 0.15524 ms | 0.15314 ms | -0.0021 ms | -0.0084 ms |
| Jetson AGX Orin | 0.4901 ms | 0.4942 ms | +0.0041 ms | +0.0164 ms |

2 -> 4 arms moves the DoF-dependent encoder + decoder by <=0.005 ms per module call (<=0.02 ms per policy call), within build-to-build spread on every board. Thor's delta is slightly negative (noise).

## 5. Accuracy: closed-loop task success across boards (MEASURED, 2026-09-18; Thor fp16 2026-10-12)

RoboCasa GR1 tabletop PnPMilkToMicrowaveClose (Fourier GR1, arms+waist+hands, 29-DoF action), 20 seeds (0-19) x 720 sim steps, 20 Hz control, 16-step action chunks, 4 denoise steps. Policy: youliangtan/gr00t-n1.5-robocasa-tabletop-posttrain @ b46fb3c (GR00T N1.5 post-trained on the RoboCasa tabletop tasks); PyTorch (not TensorRT) on every backend. one diffusion-noise bank (seed 5000, 20x50x1x16x32 fp32) injected bit-identically into every backend; scenes deep-reseeded per seed; per-(episode, call) noise pairing.

|---|---|---|---|---|---|---|---|
| RTX 5090 (reference) | bf16 | 9/20 | [0.2582, 0.6579] | — | — | — | — |
| Jetson AGX Orin | fp16 | 9/20 | [0.2582, 0.6579] | 20/20 | — | 0.043 | 338.9 ms |
| Jetson AGX Thor | fp8 | 10/20 | [0.2993, 0.7007] | 17/20 | [7, 8, 10] | 0.093 | 136.2 ms |

**Thor fp16 run (2026-10-12)**, same harness, run from this repo on Thor (torch 2.14.0+cu130, transformers 4.51.3, tokenizers 0.21.4, huggingface_hub 0.35.3). Same board, fp16 vs a bf16 control re-run in the same environment: 18/20 same outcome (flips [7, 10]), arm rel_mae 0.066. **fp8 isolated on the same board** (Thor fp8 vs Thor bf16): 18/20 same outcome, flips [8, 10], arm rel_mae 0.101. Thor fp8's flips vs the 5090 decompose into one hardware/stack flip (seed 7, which also flips under Thor bf16) and two fp8-precision flips (seeds 8 and 10).

**fp8 really ran:** 391 Linear layers converted, 664,200 `torch._scaled_mm` calls with torch.float8_e4m3fn operands over the 900 policy calls. 664,200 e4m3 GEMMs / 900 policy calls = 738 per call = 165 (SigLIP) + 84 (Qwen LLM, select_layer 12) + 1 (mlp1) + 24 (VL self-attn) + 4 x 116 (DiT per Euler step). Attention, norms, patch-embed and the per-embodiment state/action encoder+decoder stay bf16.

closed-loop latencies are PyTorch eager policy calls (not TensorRT): board compute, and in-loop incl. host<->board ZMQ. On Thor, fp8 is slower than bf16 at batch 1 (dynamic-quantisation overhead): in-loop incl. ZMQ ~141 vs ~76 ms; board compute in the table. Use results/speed for deployable latency.

Caveats:

- The 5090 reference is bf16, not fp32 ground truth.
- n = 20 seeds, one noise draw per seed: Wilson 95% CIs are about +/-20 points and overlap for every backend (all ~40-50%). The data rule out a collapse, not a 10-20 point degradation; the fp8 > bf16 rate ordering is noise.
- The checkpoint authors report 0.60 for this task (SOURCED: Isaac-GR00T examples/RoboCasa/README.md at the pinned commit); our 45% (Wilson CI 26-66%) is consistent with it.
- Seed 14's initial observation is nondeterministic on the host simulator (3 distinct call-0 hashes over 7 host sweeps; not the seeded layout RNG). It is a win on every backend and in no flip; excluding it leaves the conclusions unchanged (Orin 8/19 = 5090 8/19; Thor fp8 9/19 vs 8/19).
- The 5090 reference run predates call-0 hashing, so its scene identity is inferred (host probe + call-0 action agreement <=0.013 vs ~0.30 for a different scene). The 2026-09-18 board runs hash-match each other on 19/20 seeds (all but 14); the 2026-10-12 Thor bf16 re-run also differs at seed 5, which is not a flip seed.
- Thor fp8 determinism was not tested (no repeat run); Orin fp16 is bit-exact across two processes.
- Thor fp8's flips are heterogeneous: seed 8 is a true boundary case; seed 10 is a large-divergence success (per-call rel_mae peaks at 1.70) that won the seed the 5090 lost.

Reproduce: `accuracy/run_closed_loop.py` per backend, then `accuracy/finalize.py` and `accuracy/make_summary.py` (docs/ACCURACY.md). The raw runs (per-seed success, every action chunk, server call logs) are in `results/accuracy/runs/`; `finalize.py` recomputes every number in this table from them.

## 7. Arms vs cameras: what actually scales (RTX 5090, MEASURED)

Only the action encoder + decoder grow with the number of arms. Re-run 2026-10-12 (`speed/multiarm/camera_token_scaling.py`, TensorRT 11.2.1.2): 0.0539 ms per module call, 0.2156 ms per policy call at 4 denoise steps = 3.52% of the action head. This differs from §4 (TensorRT 10.16, engines built separately) and from §2's in-pipeline encoder/decoder times (measured inside a full policy call, including hand-offs): three methods, same conclusion -- arms are a rounding error next to the backbone.

| Cameras | ViT ms (2026-10-10) | ViT ms (re-run) | LLM vision tokens | LLM ms (2026-10-10) | LLM ms (re-run) |
|---|---|---|---|---|---|
| 1 | 1.978 | 1.8611 | 256 | 1.967 | 1.6863 |
| 2 | 2.559 | 2.3662 | 512 | 2.908 | 2.8246 |
| 4 | 3.822 | 3.6993 | 1024 | 4.969 | 5.1873 |

The 2026-10-10 numbers came from an earlier, unpreserved version of this measurement (TensorRT 10.16.1); this re-run (TensorRT 11.2) re-implements its method. ViT within 6%, LLM within 15%, DoF-dependent cost per module call within 1%; VL self-attention reads 0.61 ms here vs 0.39 ms published (shape/build difference not recoverable). The conclusion -- arms cost ~0.05 ms per module call, cameras cost ~ms -- holds in both.
